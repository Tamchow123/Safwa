| 21 | **Unbounded `pending_parent` accumulation** (Phase 16, §14.2) — a client that repeatedly submits events whose parent never arrives grows a single component's held-row count over time; the per-request `existingRows`/chain load is then O(n) in that backlog (the promotion loop itself is bounded and DoS-safe). | L | L | The cross-batch reprocessor is strictly bounded (forward-walk, O(promotions)); the accumulation is a slow request-cost-growth concern, not a CPU/lock DoS. **Partially mitigated in Phase 16 (EXT-F4):** a per-component **live-pending cap** (`SYNC_BOUNDS.maxPendingPerComponent`) now rejects new holds past the bound, and each hold carries a **TTL** (`pendingExpiresAt`) so expired holds are excluded from the cap and never promoted. | 22 | **Local learner-state reads scale with the whole store, not the owner's share** (Phase 16 R2-F3, full-phase council REL-P16-001/002) — `study_attempts` has no indexed `userId` (the owner lives inside the embedded attempt payload), and IndexedDB cannot index `null`, so the GUEST branch of `readOwnedRows` also falls back to a full-store scan + in-memory filter. Accepted for Stage A (a guest's data is single-device and unsynced, so its ceiling is naturally lower). Fix path if telemetry or a support report shows it: add an indexed `userId` column to `study_attempts` in a further additive Dexie version (mirroring the v6 treatment of the other five stores), and/or bound the analytics read window. | 23 | **Sign-out wipes a coexisting guest's local data** (Phase 16, full-phase council SEC-003) — `clearAccountLocalState` clears the account-scoped stores wholesale, and since schema v6 a guest's rows share those physical tables, so a guest's own bookmarks/lists/settings/history on a shared device are destroyed when an unrelated account signs out. | M | L | **Deliberate and human-approved**, not a defect: the shared-device confidentiality guarantee is the purpose of the wipe, and a partial wipe would leave rows whose owner cannot be re-verified once the session is gone. It is data loss on a shared device, never a confidentiality leak. The behaviour is pinned by `logout.test.ts` ("wipes a coexisting GUEST's rows too") and by E2E §60.9 (commit `30fa7ee`, superseding the earlier Phase-15 "guest data survives login/logout" expectation), and stated in `docs/OFFLINE_AND_SYNC.md`. **CLOSED in Phase 17.** Dexie schema v7 puts the owner in the primary key (`[ownerKey+naturalKey]`, ADR-009), so `clearAccountLocalState` is now owner-SCOPED: the departing account's rows go and a coexisting guest's stay. Where the departing account cannot be resolved it removes every non-guest owner's rows, so the confidentiality guarantee never depends on that lookup succeeding. Pinned by `logout.test.ts` and by E2E §60.9 / §26.3. | Eng |
| 24 | **A merge failing after the guest's rows are dropped would lose the only copy** (Phase 17) — the guest's local history is not backed by anything until the account's copy is durable, so any ordering that removes it earlier is unrecoverable data loss. | H | L | Ordering is the mitigation and it is structural, not procedural: `guest-merge-finalise.ts` drops the source rows only after the server has acknowledged a durable import, in one Dexie transaction, and every failure path returns before it. Pinned by unit tests on finalisation ordering and by E2E §26.4 (a forced upload failure leaves every guest row) and §26.9. | Eng |
| 25 | **Replay's multi-root exemption could widen beyond the merge** (Phase 17, ADR-009) — a component with two chain roots is normally corruption; the merge makes it legitimate, and a future change that loosens the condition would make forged lineage indistinguishable from imported lineage. | H | L | The defence is at ADMISSION, not at replay, and it is structural: a second root is only permitted by `classifyMergeLineage`, a SEPARATE exported entry point from ordinary sync's `classifyLineage` with no flag connecting them, requiring a brand-sealed `MergeUnionContext`, and reached only for an event carrying `imported_from_guest_import_id` — which only the authenticated merge coordinator stamps. Picking the wrong entry point fails CLOSED (a legitimate merge event is rejected and a test catches it). Replay is deliberately NOT a second check: it tolerates the shape on `study_components.merged_at` alone and never re-verifies per-event provenance (DATA_MODEL §4.1, ADR-009), so a change to the admission path deserves more scrutiny than a change to replay. Integration tests assert the refusal as well as the acceptance. Phase 19's device-conflict resolution is explicitly forbidden from reusing it. | Eng |
| 26 | **A deletion requested on one device and confirmed on another leaves the first device's rows** (Phase 17) — the nonce that authorises the local clear lives on the requesting device, so confirming from a phone does not clean a laptop. | L | M | Accepted and documented (DATA_MODEL §9.2) rather than closed by a weaker rule: the alternatives all infer deletion from something a bad network can fake, and the penalty for inferring wrongly is destroying a live account's unsynced work. The rows in question can no longer sync to anything, and the laptop's next sign-out clears them by the ordinary owner-scoped path. | Eng |

| 27 | **"Export my data" is not a backup and cannot be imported** (Phase 18) — `modules/profile/export.ts` produces a `SafwaDataExport` JSON file, and **nothing in the codebase reads one back**: no import path, no route that accepts one, no parser, no code that consumes a `SafwaDataExport` value it did not itself just build. (The module is of course used — `components/settings/data-settings.tsx` calls it to produce the download. The missing half is the reverse direction, not the module.) A learner who exports before clearing their browser, or before a device dies, holds a file this app cannot restore from. | M | M | Recorded rather than fixed, because an importer is a separate feature with its own merge semantics (it would have to reconcile against a causal event DAG, which is the hard part of Phase 19's work, not a serialisation exercise). The real restore path for account data is the nightly encrypted `pg_dump` chain and its quarterly drill (DEPLOYMENT §7); the export is for portability and inspection, not recovery. The asymmetry is written down here precisely so the button is never mistaken for a backup in a support conversation. **Guest data has no server-side copy at all**, so for a guest the export genuinely is the only artifact — and it is still not restorable. Fix path if a learner ever needs it: an importer that treats the file as a guest→account-merge-shaped input and reuses `classifyMergeLineage`'s admission discipline, never a raw row insert. | Eng/Product |
| 28 | **An offline shared device resolves to the last account that used it** (Phase 18, §2 of phases-18.md) — the durable last-known-owner memory that fixes the offline-identity defect has **no TTL**, and is forgotten only by the three triggers in phases-18.md §2.1 (a session that classifies as **guest**, an explicit **sign-out**, and **account deletion** — that last one because a TTL-free memory would otherwise outlive the account it names: delete, re-register, go offline before the new account's first session check, and it would stamp fresh reviews with a dead owner key). Closing the tab is not a trigger, and a different account signing in overwrites the memory rather than clearing it. So learner A closing the tab without signing out, followed by learner B opening the app **offline** on the same device, means B's study is attributed to A. | L | M | Accepted, and it is the lesser of two bad options: the alternative — treating an unresolvable offline session as a guest — is the exact defect this phase exists to fix, and it silently discards a signed-in learner's work (rows stamped `guest` are never uploaded). Attributing to the last known owner is recoverable by a sign-out; attributing to a guest is not recoverable at all. The window is also narrower than it reads: it needs no network AND no sign-out AND a second person on the same device. Mitigations in place: the three forget triggers, and an honest offline status indicator rather than a fake "Synced". Documented in `OFFLINE_AND_SYNC.md`'s Phase 18 section under what is explicitly NOT guaranteed, and in the offline identity contract itself. Revisit if Safwa ever gains a genuinely shared-device deployment, where a short TTL becomes worth its cost. | Eng |
| 29 | **No automated check proves offline study works on iOS** (Phase 18, phases-18.md §8.1) — Playwright's WebKit cannot emulate an offline navigation at all: every navigation under `setOffline(true)` fails with an internal error, including in a context with service workers blocked that goes offline before its first navigation. So the offline journey, the unvisited-route fallback and the checksum-recovery test are pinned to Chromium. | M | M | Measured, documented, and compensated rather than hidden. WebKit still runs everything it can observe — the worker registers and controls the page, `install` precaches `/~offline`, browsing fills the document, build-asset and content-pointer caches, plus the §10 installability criteria and the 44px touch targets — which is every part of the mechanism except serving a navigation with the network off. The residue is **H4**, a real install on a real iPhone in airplane mode, which is a stronger check than WebKit could have given; it is therefore load-bearing for acceptance criterion 1 on iOS rather than a formality. `phases-18.md` §11 records that a green CI run must never be read as "offline works on iPhone". Reopens automatically if a Playwright release makes WebKit return an ordinary network error for an offline navigation — at which point deleting one `test.skip` is the whole change. | Eng |
| 30 | **A service worker outlives the deploy that installed it** (Phase 18) — a worker lives on the device, not in the page, so redeploying an earlier build does not remove one. A bad worker keeps controlling every navigation and serving its own caches until something explicitly unregisters it. | L | H | The rollback is a deploy with the switch OFF, not a deploy of an older build: `NEXT_PUBLIC_SW_ENABLED=false` + rebuild, after which every device that loads the app unregisters **every** registration for the origin and deletes **every** cache on it, Serwist's precache included (DEPLOYMENT §8a documents the full procedure and why the two steps run independently). Two residual limits are stated rather than papered over: it is a `NEXT_PUBLIC_*` variable so it is inlined at build time and changing it without a rebuild changes nothing; and a device that never loads the app again keeps its worker, with the browser's own "Clear site data" as the only remaining lever. Confidentiality is bounded independently of all this: `/api/**` is `NetworkOnly` so no learner data is ever cached, and the two caches that can hold account-specific markup are cleared on sign-out. | Eng |

## Pre-launch gate (must be resolved or accepted in writing before Production launch)

1. Risk 1: redistribution permission confirmed, or a documented decision with
   takedown/replacement plan.
2. Risks 3/4: exclusion tests green; no unverified content reachable by
   learners.
3. Risk 9: Multi-device offline Beta suite green across supported browsers.
4. Risk 11: security pass completed; rate limits verified.
5. Backups restored successfully in a drill (DEPLOYMENT §7).
