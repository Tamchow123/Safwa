Product, Ops. Review this register at every milestone (Guest Alpha, Core MVP,
each Beta, Launch); no unmitigated High-impact risk may ride into Production

| 21 | **Unbounded `pending_parent` accumulation** (Phase 16, §14.2) — a client that repeatedly submits events whose parent never arrives grows a single component's held-row count over time; the per-request `existingRows`/chain load is then O(n) in that backlog (the promotion loop itself is bounded and DoS-safe). | L | L | The cross-batch reprocessor is strictly bounded (forward-walk, O(promotions)); the accumulation is a slow request-cost-growth concern, not a CPU/lock DoS. **Partially mitigated in Phase 16 (EXT-F4):** a per-component **live-pending cap** (`SYNC_BOUNDS.maxPendingPerComponent`) now rejects new holds past the bound, and each hold carries a **TTL** (`pendingExpiresAt`) so expired holds are excluded from the cap and never promoted. The remaining half — a background purge/dead-letter job that physically deletes the expired rows (so the per-request `existingRows` load also stops growing) — is deferred to the Phase 18/19 offline/resubmission work. | Eng |

| 22 | **Local learner-state reads scale with the whole store, not the owner's share** (Phase 16 R2-F3, full-phase council REL-P16-001/002) — `study_attempts` has no indexed `userId` (the owner lives inside the embedded attempt payload), and IndexedDB cannot index `null`, so the GUEST branch of `readOwnedRows` also falls back to a full-store scan + in-memory filter. Both sit behind the dashboard load (mount + every tab refocus) and the mixed/custom quiz session-start weakness snapshot. | M | L | Correctness is unaffected — the filter is exact, and every account read of the five indexed stores uses the `[userId+…]` index. The cost is latency that grows with a device's total lifetime local rows rather than the active identity's share. Accepted for Stage A (a guest's data is single-device and unsynced, so its ceiling is naturally lower). Fix path if telemetry or a support report shows it: add an indexed `userId` column to `study_attempts` in a further additive Dexie version (mirroring the v6 treatment of the other five stores), and/or bound the analytics read window. Revisit alongside the Phase-17 guest-merge work, which touches these stores anyway. | Eng |

| 23 | **Sign-out wipes a coexisting guest's local data** (Phase 16, full-phase council SEC-003) — `clearAccountLocalState` clears the account-scoped stores wholesale, and since schema v6 a guest's rows share those physical tables, so a guest's own bookmarks/lists/settings/history on a shared device are destroyed when an unrelated account signs out. | M | L | **Deliberate and human-approved**, not a defect: the shared-device confidentiality guarantee is the purpose of the wipe, and a partial wipe would leave rows whose owner cannot be re-verified once the session is gone. It is data loss on a shared device, never a confidentiality leak. The behaviour is pinned by `logout.test.ts` ("wipes a coexisting GUEST's rows too") and by E2E §60.9 (commit `30fa7ee`, superseding the earlier Phase-15 "guest data survives login/logout" expectation), and stated in `docs/OFFLINE_AND_SYNC.md`. **CLOSED in Phase 17.** Dexie schema v7 puts the owner in the primary key (`[ownerKey+naturalKey]`, ADR-009), so `clearAccountLocalState` is now owner-SCOPED: the departing account's rows go and a coexisting guest's stay. Where the departing account cannot be resolved it removes every non-guest owner's rows, so the confidentiality guarantee never depends on that lookup succeeding. Pinned by `logout.test.ts` and by E2E §60.9 / §26.3. | Eng |
| 24 | **A merge failing after the guest's rows are dropped would lose the only copy** (Phase 17) — the guest's local history is not backed by anything until the account's copy is durable, so any ordering that removes it earlier is unrecoverable data loss. | H | L | Ordering is the mitigation and it is structural, not procedural: `guest-merge-finalise.ts` drops the source rows only after the server has acknowledged a durable import, in one Dexie transaction, and every failure path returns before it. Pinned by unit tests on finalisation ordering and by E2E §26.4 (a forced upload failure leaves every guest row) and §26.9. | Eng |
| 25 | **Replay's multi-root exemption could widen beyond the merge** (Phase 17, ADR-009) — a component with two chain roots is normally corruption; the merge makes it legitimate, and a future change that loosens the condition would make forged lineage indistinguishable from imported lineage. | H | L | The defence is at ADMISSION, not at replay, and it is structural: a second root is only permitted by `classifyMergeLineage`, a SEPARATE exported entry point from ordinary sync's `classifyLineage` with no flag connecting them, requiring a brand-sealed `MergeUnionContext`, and reached only for an event carrying `imported_from_guest_import_id` — which only the authenticated merge coordinator stamps. Picking the wrong entry point fails CLOSED (a legitimate merge event is rejected and a test catches it). Replay is deliberately NOT a second check: it tolerates the shape on `study_components.merged_at` alone and never re-verifies per-event provenance (DATA_MODEL §4.1, ADR-009), so a change to the admission path deserves more scrutiny than a change to replay. Integration tests assert the refusal as well as the acceptance. Phase 19's device-conflict resolution is explicitly forbidden from reusing it. | Eng |
| 26 | **A deletion requested on one device and confirmed on another leaves the first device's rows** (Phase 17) — the nonce that authorises the local clear lives on the requesting device, so confirming from a phone does not clean a laptop. | L | M | Accepted and documented (DATA_MODEL §9.2) rather than closed by a weaker rule: the alternatives all infer deletion from something a bad network can fake, and the penalty for inferring wrongly is destroying a live account's unsynced work. The rows in question can no longer sync to anything, and the laptop's next sign-out clears them by the ordinary owner-scoped path. | Eng |

## Pre-launch gate (must be resolved or accepted in writing before Production launch)

1. Risk 1: redistribution permission confirmed, or a documented decision with
   takedown/replacement plan.
2. Risks 3/4: exclusion tests green; no unverified content reachable by
   learners.
3. Risk 9: Multi-device offline Beta suite green across supported browsers.
4. Risk 11: security pass completed; rate limits verified.
5. Backups restored successfully in a drill (DEPLOYMENT §7).
